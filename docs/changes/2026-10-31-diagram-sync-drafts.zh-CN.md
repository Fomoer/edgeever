# 同步时保留图表草稿

## 问题与目标

[Issue #737](https://github.com/tianma-if/edgeever/issues/737) 反馈思维导图编辑内容消失，而客户端显示已同步。共用图表编辑器在笔记版本变化时清除未保存状态，并在内容哈希变化时重载画布，没有保护更新的本地草稿。本次修复应保留这些编辑，并使保存状态准确。

## 允许变更与验收

- 思维导图、流程图和架构图的共用编辑器接收笔记快照时，不覆盖未保存的画布、标题、标签、节点文字输入或大纲编辑。本设备的同步回执可以推进并发版本基线，但不能丢弃草稿、取消其自动保存或清除撤销历史。
- 新笔记的临时 ID 映射为服务端 ID 时，仍视为同一编辑会话，保留画布、焦点和未保存输入。输入期间暂缓的远端快照，在取消输入或草稿恢复到已保存基线后继续应用；真正改动过的草稿不自动变更到远端内容的版本基线。
- 本地保存尚未完成时产生的编辑，必须保留未保存状态，直到其自身保存完成。保存回执只能确认该请求所属的笔记、画布和提交的快照；用户已经开始编辑另一个节点时也须遵守。
- 没有本地草稿时继续应用真正的远端修改。编辑期间收到真正的远端修改时，保留草稿及其原并发版本基线，沿用现有同步冲突处理。
- 新增定向浏览器回归：延迟同步回执，直到产生后续画布编辑或节点文字输入，验证编辑仍在，并在自动保存、重新打开后从持久存储读回。版本号变化、内容哈希变化、元数据和空闲编辑器接收远端修改，复用同一定向流程或现有隔离复现进行覆盖。回归数据不依赖已有标签或当前选中的笔记本；浏览器会话初始化前，通过 Web 代理等待 API 健康就绪。
- 运行受影响的图表检查、`bun run typecheck`、`bun run typecheck:mobile` 和 `bun run build:web`；检查实际界面并操作编辑、保存流程。分别记录桌面客户端与浏览器的验证范围。
- 在 PR 的 v2.16.0 基线与修复后的渲染器上，通过相同的 macOS 原生开发入口截取受控修复前后对比：暂缓真实保存回执，进行相同的后续节点和标题编辑，再放行回执。分别展示两版在回执到达前后的状态，并在自动保存后检查本地及服务端内容。
- 桌面端 `memo.create` 请求保留队列中的结构化 `contentJson`，复用已有 API 字段和资源 URL 规范化；仍支持只有 Markdown 的旧队列；验证未修改的 v2.15.0 原生端留下的待上传创建队列，在同一 SQLite 数据目录切换修复版渲染器后可以上传并继续编辑。不放宽异常覆盖保护。验证新建图表后修改标题和节点可成功上传，序列化元数据不再被计入正文。
- 通过项目标准的本地开发入口验证 macOS 原生客户端，使用项目固定版本的 Electron，以及由 v2.15.0 源码本地编译的 Rust sidecar。Linux 原生端使用 Xvfb 和正式 v2.15.0 运行时。两端均使用在对应源码上仅应用本任务修复后构建的渲染器。使用临时应用数据、数据库和测试服务，禁用自动升级，不替换已安装客户端或修改已有服务。

## 保持不变的边界

保留现有 1,200 ms 自动保存延迟、输入规则、保存失败行为、Repository 入口、同步协议、冲突解决、数据库结构、备份和原生平台实现。不修改文本、表格、海报或信息图编辑器，不新增依赖，不发布版本。已有第三方笔记导入改动不属于本次任务。

## 风险与回滚

同步回执判断错误可能隐藏真正的远端修改，或把草稿推进到错误的并发版本基线。分别验证自身同步和真正的远端更新。桌面创建请求的改动影响服务端初始正文及其哈希；结构化文档不匹配时可能损坏初始表示。验证结构化队列及只有 Markdown 的旧队列，并在 macOS、Linux 原生端操作真实创建、编辑、同步和重启流程。回退图表快照协调和桌面创建字段透传即可恢复原实现，无需数据迁移。

## 完成核对

- 产品改动仅涉及 `DiagramEditorPane.tsx`，以及 `desktop-sync.ts` 中桌面端的 `memo.create` 请求。快照协调保留本地草稿和正在输入的内容，单独推进自身同步基线，刷新编辑会话时不再阻断自动保存，并把保存回执绑定到原逻辑笔记和画布。复用现有编辑器身份辅助函数，在 ID 映射时保留图表、大纲和焦点。取消输入或草稿恢复已保存基线后继续应用暂缓的远端更新，判断依据包括实际的大纲和未保存状态，不再仅依赖聚合标记；新保存的本地草稿仍保留原并发基线，沿用现有冲突处理。
- `tests/e2e/memo-sync-race.spec.ts` 的 3 个 Chrome 场景通过，包含原有文本光标回归。图表场景验证：延迟真实 API 回执后，节点、标题和标签编辑均保留并可重新打开读回；新笔记 ID 映射时保留焦点和原画布，随后可保存并重新打开；空闲时接受远端更新，未修改节点输入后取消、标签回到原值后恢复大纲删除时也会继续应用更新。真正编辑期间收到远端修改时，草稿的原版本号/哈希保持不变。在已安装 Playwright 浏览器的环境运行 `bunx playwright test tests/e2e/memo-sync-race.spec.ts --grep 'mind-map'` 可复验。
- 隔离浏览器检查延迟了本地保存，并在此期间继续修改标题和另一个节点；还在无效大纲正在输入时进行了 ID 映射。草稿、输入焦点和原画布均保留，后续保存使用已确认版本；自身同步后输入和撤销仍可操作。已检查实际编辑器界面。
- 67 项图表编辑器、快照、编辑器身份和桌面同步检查均通过，覆盖结构化创建内容及只有 Markdown 的旧队列。包含两项修复的代码通过 `bun run typecheck`、`bun run typecheck:mobile` 和 `bun run build:web`。
- Linux 打包运行时在 Xvfb 下的检查通过，使用正式 v2.15.0 Electron/sidecar 与修复后的渲染器：延迟同步回执时保留后续节点和标题编辑；临时 ID 映射时保留原画布和输入焦点；空闲及取消未修改输入后接受真正的远端更新。两张导图均可从真实 sidecar SQLite 和服务端读回，并在完整退出、重启客户端后保留，包括创建期间同时修改标题和节点的新导图。
- 桌面创建请求现已携带规范化后的结构化 `contentJson`，创建时不再把序列化图表元数据计入正文，后续标题和节点修改可上传；未放宽 `suspicious_memo_overwrite` 保护。未修改的 v2.15.0 原生客户端通过 sidecar 写入的待上传创建队列，在同一 SQLite 数据目录切换修复版渲染器后上传成功，可继续修改，并在再次完整重启后保留；队列无待处理、失败或冲突项。
- macOS 原生客户端通过标准本地开发入口完成相同四项回归：延迟同步回执、ID 映射期间的输入焦点、真正的远端更新，以及完整重启后的持久化读回。使用 v2.15.0 源码、Electron 44.7.0、本地编译的 Rust sidecar、真实 SQLite 和真实测试 API。本次覆盖原生功能；签名安装包及自动升级验收仍由 Release 工作流负责。Windows 原生端尚未验证。

## macOS 原生端受控修复前后对比

未修改的 v2.16.0 基线（`01422910`）与修复后的渲染器（`e0e1b678`）使用相同的标准原生开发入口、Electron 44.7.0、Rust sidecar、真实 SQLite 和真实 API。两版窗口均为 1440 × 900，截图截取相同的编辑器区域，缩放均为 100%。

1. 打开含 8 个节点的思维导图，把标题改为“上次自动保存的标题”。让真实 API 写入这次自动保存，但暂缓返回回执。
2. 在下一次 1,200 ms 自动保存前，新增“【新增】回执返回也不能丢”，标题改为“刚输入的新标题（不能丢）”。暂停渲染器时钟，使这份草稿保持待保存，再放行旧回执。
3. 推进时钟 1,400 ms 并同步，读取原生 SQLite 与服务端笔记，再完整退出、重启原生客户端并重新打开笔记。测试不改写 API 回执或笔记数据。

| 阶段 | 修复前 | 修复后 |
| --- | --- | --- |
| 旧回执尚未返回 | 新标题、9 个节点、未保存 | 新标题、9 个节点、未保存 |
| 旧回执返回 | 标题回退；9 个节点暂时仍可见，却错误显示已同步 | 新标题和 9 个节点保留，正确保持未保存 |
| 自动保存并重新打开 | 本地和服务端均未收到新增节点；重开仅剩 8 个节点及旧标题 | 本地和服务端均保存新节点及标题；重开仍为 9 个节点、已同步 |

本场景的节点是在重开后消失，而不是回执返回瞬间消失：错误的已保存状态取消了后续自动保存。[原生端与 API 实测记录](evidence/2026-10-31-diagram-sync-drafts/macos-controlled-comparison.json)。
